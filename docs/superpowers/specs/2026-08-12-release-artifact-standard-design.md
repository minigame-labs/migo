# Release artifact standard

## Problem

`v0.9.1` published 25 assets. Only 9 are payloads; the rest is metadata, and three
separate naming schemes coexist:

- `migo-full-release-arm64-v8a.aar` — Gradle's internal `<profile><buildType>` task
  name leaked into a public filename
- `migo-sdk-android-arm64-v8a.tar.gz` — `sdk-` prefix
- `migo-linux-x86_64.tar.gz` / `migo-ohos-x86_64.tar.gz` — no prefix

No asset carries a version, and the arch vocabulary mixes Android ABI names
(`arm64-v8a`) with GNU triple names (`aarch64`, `x86_64`).

Three defects sit underneath the cosmetics.

**The checksum manifest's coverage is a lie.** `SHA256SUMS.txt` is generated by
`release.yml:608-611` as `cd platforms/android/dist && sha256sum *`, so it covers only
the Android job's output. The Linux, Windows and OHOS assets are uploaded by hand and
appear in no checksum manifest, while the file's name implies whole-release coverage.

**`scripts/publish-release.sh` is a decayed second source of truth.** Its
`required_files` still names v0.9.0-era assets (`migo-android-java.aar`,
`migo-android-capi-*`), its release-notes body hardcodes "Migo v0.9.0", and it asserts
an asset count of exactly 10. It and `release.yml` describe the same thing and have
fully diverged.

**One release mixes two provenance levels.** CI builds Android only —
`release.yml`'s single upload step lives inside `release-android`. Linux, Windows and
OHOS packages are `tar`red on a release machine, so the `package_sha256` their
attestations swear to is unreproducible by any recipient, even though
`scripts/package-sdk.sh` plus `scripts/test-sdk-package-reproducibility-contract.sh`
exist as the reproducible path.

Two smaller gaps found while measuring the above:

- `release.yml:25-28` runs the snapshot freshness gate for `host/full` and `host/slim`
  only (`check-snapshot-freshness.sh:18` defaults `SNAPSHOT_KIND=host`), while
  `build-snapshot.yml:94-96` runs all three. A stale `SNAPSHOT-worker-full-*.bin`
  passes the release gate.
- Nothing verifies that a recorded snapshot is actually *in* the binary.
  `generate-android-artifact-manifests.py:353-361` unconditionally validates the host
  snapshot and refuses to emit a slice if it is missing or stale, and
  `test-android-release-manifest-gate.sh` proves a release AAR cannot skip manifest
  generation — so a release cannot ship a *stale snapshot file*. But `runtime-v8/build.rs`
  makes its own, independent embedding decision and fails *safe*: an invalid snapshot
  prints `cargo:warning` and falls back to loading JS from source. Two implementations of
  one rule, and the weaker one governs the bytes. The slice can therefore claim a snapshot
  the `.so` does not contain, which is a silent cold-start regression with nothing red.

## Decisions

### D1 — Naming: `migo-<version>[-capi]-<platform>[-<arch>].<ext>`

| Kind | Name |
| --- | --- |
| Java/Kotlin AAR | `migo-0.9.1-android.aar` |
| C ABI SDK | `migo-0.9.1-capi-<platform>-<arch>.tar.gz` |
| SBOM | `migo-0.9.1-sbom.cdx.json` |
| Clerical | `version.json` (and `SHA256SUMS.txt` from phase 3) |

Arch vocabulary is `arm64` and `x86_64` everywhere in public names. `arm64-v8a`
survives only where Android mandates it (`jni/arm64-v8a/` inside the AAR);
`aarch64` survives only as a Rust target-triple component inside build scripts.

Rationale:

1. **GitHub sorts release assets by case-insensitive filename.** Verified against
   `v0.9.1`, whose API order is `migo-* → SHA256SUMS → size-report → version` — that is
   alphabetical, not upload order. Leading segments therefore control page grouping.
   This scheme lists the AAR first, then every C SDK grouped by platform, then
   metadata. Platform-first naming splits the Android assets apart
   (`arm64` < `capi-…` < `universal`).
2. **Version immediately after the product name** matches Node
   (`node-v20.11.0-linux-arm64.tar.gz`), Go (`go1.22.linux-arm64.tar.gz`) and Rust,
   and lets tooling prefix-match all assets of one version.
3. **One word per concept.** Node and Go both publish `arm64` despite GNU triples
   saying `aarch64`. `x86_64` is kept over `x64` because the repo already uses
   `x86_64` in triples, script arguments and manifest names — switching would add a
   translation layer rather than remove one.
4. **Do not repeat what the extension states.** `.aar` already means "Android,
   Java/Kotlin", so no `java` segment; `.tar.gz` carries no API-surface information,
   so `capi` is required. Asymmetry that carries information beats symmetry that
   repeats it.

The version segment is derived from `release/VERSION`, the single version source
enforced by `scripts/test-release-version-contract.sh`.

### D2 — Publish one AAR, not four

`full`/`slim` and `universal`/`arm64-only` both disappear from the public surface.

Measured size deltas: full vs slim is 34.49 vs 33.26 MB universal (3.6%) and 17.19 vs
16.58 MB arm64 (3.5%), while slim drops five whole API groups — `api-sensors`,
`api-media`, `api-connectivity`, `api-commerce`, `api-system`, covering camera, audio,
bluetooth, payment, Toast/Modal, ads and Worker. Trading 3.5% size for half the API
surface is not a choice worth offering.

`universal` vs `arm64-only` is a real 2× size difference, but the consumer's build
system already owns that choice: `abiFilters 'arm64-v8a'` strips unwanted `jniLibs`
from all dependencies including AARs, and an App Bundle makes Play deliver per-ABI
automatically, so x86_64 contributes zero to end-user download size. The stated reason
for the arm64-only variant (`release.yml:541-546`: "quoting the multi-ABI size at an
integrator overstates it by roughly double") is a sales-conversation problem, solved by
documenting "34 MB contains two ABIs; a shipped arm64-only app carries 17 MB".

The deciding test for both, and for future variants: **does the consumer's build system
already own this choice?** If yes, shipping a variant transfers decision cost to the
consumer and doubles the support surface. If no — a static library cannot select its
own architecture at link time — the variant is mandatory. This is why the C SDK stays
split per arch while the AAR does not: a 365 MB `libmigo_capi.a` is a build-time input
whose consumer already knows their target, whereas an AAR's `.so` set is pruned
downstream. Size deltas are not the test; they have no principled threshold.

`full` and `slim` remain internal profiles. CI keeps building both and keeps running
`scripts/test-product-profiles.sh`; only `full` is uploaded.

### D3 — Source archives are not a choice

GitHub attaches "Source code (zip/tar.gz)" to every tag automatically and offers no
API to remove or disable them. The only available action is a release-notes line
stating that the archives are generated by GitHub and that building from source should
use the tag.

### D4 — V8 snapshots stay embedded, and the platform gap is a separate project

Snapshots are not files in a package. `runtime-v8/build.rs:136-138` gates embedding on
`target_os == "android"`, so Android artifacts report `snapshot_policy: "embedded"`
(`gen-android-package-metadata.py:200`), Linux reports `"none"`
(`gen-linux-package-metadata.py:44`), and Windows and OHOS declare nothing at all.
Linux, Windows and OHOS consumers therefore run the from-source JS path with a
measurably slower cold start.

Shipping `.bin` files as separate assets is rejected: a snapshot is bound to one exact
V8 build, so separating it from the binary manufactures version-mismatch opportunities
and adds runtime path resolution. Evidence for the binding:
`SNAPSHOT-full-aarch64.bin` and `SNAPSHOT-full-x86_64.bin` are byte-identical in
length (2158052) but differ in md5, and each `.manifest.json` records a
`v8_archive_sha256`. Android x86_64 links `librusty_v8-x86_64.a` while Linux x86_64
links `librusty_v8-x86_64-linux-gnu.a` — different archives, so different snapshots.

The correct fix is extending embedding to linux/windows/ohos, which requires an OS
dimension in the snapshot filename (`SNAPSHOT-{profile}-{arch}.bin` currently collides
android-x86_64 with linux-x86_64) and a generator run on each target platform.
Generation feasibility, not code, is the constraint: Linux x86_64 runs natively,
Windows needs a Windows host, OHOS needs an OHOS device or emulator. That is out of
scope here and handed to a machine that has the environments.

In scope here: the OHOS package manifest must declare `snapshot_policy` explicitly
instead of omitting the field, so the gap is a visible fact rather than an absence, and
an Android AAR must be proven to contain the snapshot bytes its slice manifest claims.

### D5 — The invariant is "no published asset is unverifiable", not "one checksum file"

A single `SHA256SUMS.txt` and per-asset `.attestation.json` sidecars are not
interchangeable designs; each fits a different provenance model. A sidecar is produced
next to its own artifact by whoever built it, so it composes across build machines. A
single checksum manifest requires one publisher that sees every asset. That is why this
repo grew sidecars, and why today's `SHA256SUMS.txt` lies: it is a centralised
mechanism applied to decentralised provenance.

Picking one mechanism and declaring the other wrong is what forces a phase ordering.
The property actually wanted admits both:

> Every published asset is covered either by `SHA256SUMS.txt` or by its own
> `.attestation.json`, and no published asset is covered by neither.

`scripts/verify-release-assets.sh` enforces exactly that against the published release,
so the guarantee holds under mixed provenance instead of being deferred until provenance
is uniform. `SHA256SUMS.txt` is generated by the publish job over everything that job
uploads — so it never over-claims — and a platform that is not yet built in CI carries
a sidecar.

This makes the mechanism count a consequence rather than a decision: as each platform
moves into CI its sidecar disappears on its own, and when the last one does, the sidecar
branch of the invariant has zero members and is deleted. That final deletion is the
cross-repo change to `resolve-migo-artifact.sh` in `migo-examples`, which verifies
downloads against sidecars today.

### D6 — One publish job, one staging directory, one upload glob

`release.yml` currently keeps the asset list in three hand-copied places: the
"Verify Android release artifacts are present" name list (18 entries), the
`files:` block of the publish step (20 patterns), and the implicit
`sha256sum *` coverage. Any one of them can be missed. The deeper problem is that
publishing lives *inside* `release-android`, so there is no point in the graph that sees
every platform's output — which is what makes a whole-release checksum manifest
impossible today.

Split publishing out. Each platform job builds and stages its assets under canonical
names and uploads them as a workflow artifact. A `publish` job that `needs` every
platform job downloads them into one `dist/release/`, generates `SHA256SUMS.txt` and
`version.json`, and performs the single `files: dist/release/*` upload. Adding a
platform later is then purely additive: one job plus one entry in `needs`.

Two guards replace the hand-copied lists:

- `scripts/test-release-asset-naming-contract.sh <dir>` — every file in the directory
  matches D1's pattern and its version segment equals `release/VERSION`. Explicitly
  exempts `version.json` and `SHA256SUMS.txt`, stating why: their URLs must be
  predictable across versions. This subsumes the `rm -rf platforms/android/dist`
  precaution, since a stale asset from an older naming scheme now fails the gate
  instead of being silently uploaded.
- `scripts/verify-release-assets.sh <tag>` — reads the published asset set from the
  releases API and asserts it equals the expected set exactly, and that D5's invariant
  holds for every asset. This is the only check that can catch an asset uploaded outside
  the process, and it verifies published state rather than build intent.

No new naming library is introduced. `package-sdk.sh:66-79` already derives the asset
name from the staged prefix directory, with the comment "Deriving it means there is no
second naming scheme"; the change is its format string plus reading `release/VERSION`.
`build-aar.sh:551` owns the AAR name the same way. Two producers with one format string
each, both deriving the version from the one enforced source.

### D7 — All-CI is the destination; local build is not

Every blocker to building a platform in CI has the same shape: a large binary
dependency that is not yet in a downloadable place. The repo already has the mechanism
for that shape — a `v8-archives-<rev>` release tag plus `fetch-v8-archives.sh`, which
fails closed on a missing or mismatched archive.

| Platform | Runner | Blocker |
| --- | --- | --- |
| Android AAR + C SDK | ubuntu-latest | none, already in CI |
| Linux x86_64 | ubuntu-24.04 | none — `fetch-linux-sysroot.sh` exists, `librusty_v8-x86_64-linux-gnu.a` is already on `v8-archives-e6a88b3` |
| Windows x86_64 | windows-latest | `rusty_v8.dll` + import lib not yet on any archive tag; ANGLE DLL provenance must be pinned |
| OHOS arm64/x86_64 | ubuntu-latest | OHOS SDK has no official action; the OHOS V8 archive was built locally but never published to a tag |

Neither Windows nor OHOS is infeasible; each needs a one-time upload. Fragmentation is
the current state, not a risk of the change.

Android cross-compilation already covers both ABIs in CI (`release.yml:539` builds both
`.so` sets via cargo-ndk; `release.yml:566` loops `aarch64 x86_64` for the C SDK).
Snapshot *generation* is asymmetric — `ubuntu-latest` has `/dev/kvm` so x86_64 runs on
a hardware-accelerated emulator (`build-snapshot.yml:187-202`), while
`ubuntu-24.04-arm` exposes no `/dev/kvm` so arm64 requires a real device
(`build-snapshot.yml:17-21`) — but this does not constrain releases, because snapshots
are committed repository assets that the release only validates and embeds.

## Structure first, then coverage

This is not phased by effort. The final structure lands in one change. What fills in
afterwards is *platform coverage*, because two platforms are blocked on artifacts only
the maintainer can publish — see Blockers.

### Step 1 — Final structure, with Android and Linux built in CI

Published set, 17 files (from 25). The earlier count of 13 undercounted: the CI-built
payloads carry attestation sidecars too, because `package-sdk.sh` and `build-aar.sh`
generate them as part of the reproducible packaging path. Those are now redundant with
`SHA256SUMS.txt`, and D5 says so — they are what disappears when the last platform moves
into CI, together with the `migo-examples` change. Removing them earlier would break
`resolve-migo-artifact.sh` while `SHA256SUMS.txt` still does not cover every platform.


```
CI-built, covered by SHA256SUMS.txt
  migo-0.9.1-android.aar                      34 MB
  migo-0.9.1-capi-android-arm64.tar.gz        71 MB
  migo-0.9.1-capi-android-x86_64.tar.gz       69 MB
  migo-0.9.1-capi-linux-x86_64.tar.gz         72 MB
  migo-0.9.1-sbom.cdx.json
  SHA256SUMS.txt
  version.json

hand-built until step 2, each covered by its own sidecar
  migo-0.9.1-capi-ohos-arm64.tar.gz          ~88 MB   new — arm64 is the device arch
  migo-0.9.1-capi-ohos-x86_64.tar.gz          88 MB
  migo-0.9.1-capi-windows-x86_64.tar.gz       27 MB
  + one .attestation.json each
```

Work:

1. `build-aar.sh` emits `migo-<version>-android.aar` for the published artifact;
   internal Gradle outputs keep their `<profile><buildType>` names.
2. `package-sdk.sh` derives `migo-<version>-capi-<platform>-<arch>.tar.gz`, reading
   `release/VERSION` through the existing `read_release_version` helper.
   `test-release-version-contract.sh` enumerates which files may read the version and
   with what literal, so it needs a matching entry.
3. Normalise staged prefix directories to canonical arch words —
   `dist/migo-android-arm64`, `dist/migo-ohos-arm64` — rather than mapping vocabularies
   inside `package-sdk.sh`, which would create a second vocabulary. Touches
   `build-android-sdk.sh`, `build-ohos-sdk.sh`, their contract scripts, and the
   `release.yml` loop arguments.
4. Drop from build and upload: both slim AARs, the arm64-only AAR,
   `size-report-*.txt` (becomes a CI artifact), `version-full.json`,
   `version-slim.json`.
5. Restructure `release.yml` per D6: `release-android` and a new `release-linux` build
   and stage into `dist/release/` and upload a workflow artifact; a new `publish` job
   `needs` both, merges them, generates `SHA256SUMS.txt` and `version.json`, and does
   the one `files: dist/release/*` upload. The 18-name verification step and the
   20-pattern list are deleted.
6. Add `scripts/test-release-asset-naming-contract.sh`, run by every platform job on its
   staged directory and again by `publish` on the merged directory.
7. Add `scripts/verify-release-assets.sh`, enforcing D5's invariant against the published
   release. Run by hand after the manual OHOS/Windows uploads; becomes a CI job in
   step 2.
8. Extend `test-release-asset-ordering-contract.sh` to assert the publish step's
   `files:` is exactly `dist/release/*`, reusing its existing PyYAML parse rather than
   adding a second workflow parser.
9. Add `--snapshot-kind worker --product-profile full` to `release.yml`'s freshness
   step. `test-release-gate-parity-contract.sh` allows release-only extra steps; the
   one-way direction means nothing in pr-ci needs mirroring.
10. Add `scripts/test-android-snapshot-embedding-contract.sh`, asserting that the bytes
    of every snapshot a slice manifest claims are actually present in that slice's
    `jni/<abi>/libmigo.so`. Run it in `release-android` after the AAR build.

    Asserting on the artifact rather than inside `build.rs` is forced, not stylistic.
    `build_snapshot.rs`'s `collect_rust_files` walks every `.rs` in the runtime-v8 crate
    directory, which includes `build.rs` itself — so making `build.rs` fail closed
    invalidates all six committed snapshots, and regenerating the aarch64 pair needs
    physical arm64 hardware (`gen-snapshot.sh`: hosted CI has no arm64 KVM). Measured by
    doing it: after the edit, `check-snapshot-freshness.sh --product-profile full`
    reported both arches stale with `runtime-v8 Rust/op sources changed`. A validator
    that cannot be changed without hardware will not be changed. The artifact gate sits
    outside the fingerprint and proves the stronger property anyway: not that the build
    script intended to embed, but that the bytes are in the binary.
11. `build-ohos-sdk.sh:282` writes its package manifest inline; add an explicit
    `snapshot_policy` field to it. Windows is deliberately excluded here:
    `build-windows-sdk.sh:280` creates `share/migo/` but writes no package manifest at
    all, so `package-sdk.sh:84-91` refuses a Windows prefix outright — which is why the
    published `migo-windows-x86_64.tar.gz` was hand-tarred. Authoring that manifest is a
    prerequisite for the Windows CI job and belongs to step 2.
12. Delete `scripts/publish-release.sh`. The manual path for the two remaining platforms
    becomes: `build-<platform>-sdk.sh` → `package-sdk.sh` →
    `test-release-asset-naming-contract.sh` → upload → `verify-release-assets.sh`.
13. Update every document that names a release asset — `README.md`, `README.zh-CN.md`,
    `BUILD.md`, `platforms/android/README.md`, `platforms/android/README_EN.md`,
    `CHANGELOG.md` — and add the abiFilters size story and the GitHub source-archive
    note to the release-notes template.

Acceptance: a dry run on a scratch tag publishes exactly the CI-built set above;
`test-release-asset-naming-contract.sh` fails when a file with an old-scheme name is
planted in `dist/release/`; `verify-release-assets.sh` fails when an asset is present
with neither a `SHA256SUMS.txt` entry nor a sidecar; the worker freshness gate fails
when a worker snapshot manifest is perturbed; the embedding assertion fails when a
snapshot file is corrupted.

### Step 2 — Windows and OHOS into CI, then the sidecar branch dies

`release-windows` on `windows-latest` and `release-ohos` on `ubuntu-latest`, each
staging into `dist/release/` through the same script and added to `publish`'s `needs`.
Once both exist, no published asset lacks a `SHA256SUMS.txt` entry, so D5's sidecar
branch has zero members: delete sidecar generation from `package-sdk.sh` and move
`migo-examples`' `resolve-migo-artifact.sh` onto `SHA256SUMS.txt` in the same change.
`verify-release-assets.sh` becomes a final CI job.

Published set: 10 files.

Whether to also adopt `actions/attest-build-provenance` (Sigstore, publicly verifiable)
is deferred to this step, because it is only meaningful once every asset is CI-built,
and it replaces the bespoke `migo-release-attestation/v1` schema rather than adding
to it.

Acceptance: a tag produces all 7 payloads with no human upload step; every package
passes `test-sdk-package-reproducibility-contract.sh`; `sha256sum -c SHA256SUMS.txt`
verifies every downloaded asset.

## Blockers

Step 2 needs two artifacts published to a release tag, which requires repository write
credentials. Neither is a code problem.

| Needed | Why | Who |
| --- | --- | --- |
| `rusty_v8` Windows x86_64 archive (`rusty_v8.dll` + import lib) on a `v8-archives-<rev>` tag | `release-windows` must fetch a verified prebuilt V8; building V8 from source on a 4-core runner does not fit the job time limit | maintainer — needs a Windows/MSVC host and release-upload rights |
| OpenHarmony `librusty_v8` archives (aarch64, x86_64) on a `v8-archives-<rev>` tag | same, for `release-ohos`. The archives were already built locally on 2026-08-10; only publishing is missing | maintainer — release-upload rights |

The OHOS SDK itself is *not* a blocker: it is publicly downloadable from Huawei's
mirror, so the job can fetch it with a pinned sha256 — the same fail-closed shape
`fetch-v8-archives.sh` already uses.

Windows has two further step-2 prerequisites, both discovered while measuring the
current release:

- `build-windows-sdk.sh:280` creates `share/migo/` but writes no package manifest, so
  `package-sdk.sh:84-91` refuses a Windows prefix outright. The published
  `migo-windows-x86_64.tar.gz` was therefore hand-tarred, not produced by the
  reproducible path. Authoring that manifest is a precondition for a Windows CI job.
- ANGLE's `libEGL.dll` / `libGLESv2.dll` / `d3dcompiler_47.dll`, which
  `build-windows-sdk.sh` copies into `bin/`, come from a local directory today. Their
  provenance must be pinned to a verifiable download before `release-windows` can be
  trusted.

## Out of scope

- Extending snapshot embedding to linux/windows/ohos (D4) — separate project, needs
  target-platform execution environments.
- Adding ARMv7 or 32-bit Android artifacts. `release.yml:504-508` keeps an ARMv7
  layout-compatibility check without shipping an ARMv7 artifact; that stays as is.
- Publishing the AAR to Maven Central.
